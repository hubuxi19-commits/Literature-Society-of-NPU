# 文苑社区平台升级设计

**日期：** 2026-08-02  
**状态：** 已完成产品确认，等待书面审阅  
**适用项目：** 西北工业大学学生文学社作品交流平台

## 1. 目标

在不重建项目、不替换现有 Supabase 生产项目、不改变现有用户 UUID、作品 ID 和内容归属的前提下，完成以下升级：

1. 将每七天可修改一次笔名的数据库迁移同步到生产环境并复核 RLS。
2. 为所有账号增加一次性找回邮箱验证，同时继续使用学号和密码登录。
3. 稳定线上数据链路，把首页和讨论页改为服务端聚合与分页查询。
4. 让作品搜索覆盖正文，每次只加载十篇作品。
5. 增加私密站内消息、回复提醒、关注、收藏、评论点赞和管理员精选。
6. 增加绑定具体版本的诗句批注，以及公开、不可变的作品版本历史。
7. 增加举报、管理员处置和审计记录。
8. 保持现有现代中文文学刊物气质，同时提高移动端字号、对比度和触控可用性。

## 2. 不变约束

- 现有 GitHub Pages + Supabase 架构继续使用，不引入自建 VPS。
- 现有生产 Supabase 项目继续承载真实用户和作品，不重新注册用户或迁移作品所有权。
- 现有 `profiles`、`works`、`likes`、`comments`、`site_settings` 五张业务表保留。
- 学号不得出现在公开资料、作品、评论、搜索结果或通知内容中。
- 找回邮箱不得公开，也不得进入普通作品查询。
- 前端只能使用 Project URL 和 publishable key；Secret key 或旧版 `service_role` 只能存在于 Supabase Edge Function 环境。
- 所有业务表持续启用 RLS；权限不能只靠隐藏前端按钮实现。
- 新诗与旧诗继续保持逐行排版、空行和原始换行。
- 数据库变化按独立迁移文件交付，测试通过并经用户确认后才能执行生产迁移。
- 未经用户确认不推送 `main`、不执行生产迁移、不删除生产数据。

## 3. 实施路线

采用分阶段升级现有 Supabase 架构的路线。每个阶段都能独立测试、迁移、启用和停用。

### 阶段 A：账号与生产安全

- 在测试项目验证并在生产项目执行 `20260802_allow_weekly_pen_name_changes.sql`。
- 增加私有找回邮箱、邮箱验证令牌、密码重置令牌和请求限速。
- 部署绑定邮箱、验证邮箱、更换邮箱、请求重置和完成重置所需的 Edge Functions。
- 未验证账号允许登录和浏览，但禁止所有写操作。
- 增加 CAPTCHA、模糊化找回响应和安全审计。

### 阶段 B：稳定读取、正文搜索与分页

- 新增服务端作品分页 RPC，一次最多返回十篇。
- 一次返回作者公开资料、点赞数量、评论数量和当前用户互动状态。
- 首页不再下载全部作品，也不再逐篇补查点赞和评论。
- 正文、标题、摘要和作者纳入服务端搜索。
- 讨论页改为独立分页查询，不再对全部作品逐篇调用 `getWork()`。
- 桌面端使用“再读十篇”，移动端在第八篇附近预取下一批。

### 阶段 C：版本与批注

- 把所有现有作品迁移为第 1 版。
- 修改作品产生不可变的新版本，作品 ID 和地址不变。
- 评论和引用批注记录其针对的作品版本。
- 恢复旧版本时复制旧内容生成新的最新版本，不删除任何历史。
- 最新作品页只展示最新版本，通过按钮进入公开历史版本。

### 阶段 D：私密社交与站内消息

- 增加评论、回复、评论获赞、优质评论推荐、关注和关注作者发新作等站内消息。
- 增加私密关注列表、私密收藏列表和评论“有启发”。
- 只有消息接收者本人能够读取、标记或删除自己的消息。
- 不通过找回邮箱发送互动信息。

### 阶段 E：治理、编辑能力与视觉复核

- 增加举报、处置记录和管理员审计。
- 所有管理员同时拥有编辑能力，不增加独立编辑角色。
- 管理员可以填写作品推荐理由、编辑点评和优质评论推荐理由。
- 投稿前显示提醒式互评清单，但不把互评设置为发布门槛。
- 完成桌面和移动端字号、对比度、焦点及触控尺寸复核。

## 4. 账号与找回邮箱

### 4.1 登录身份

Supabase Auth 的主认证邮箱继续使用由学号确定性生成的内部邮箱，因此日常登录仍然只需要学号和密码。找回邮箱单独保存，不替换 Auth 主邮箱。

### 4.2 找回邮箱规则

- 一个已验证邮箱只能绑定一个用户 UUID。
- 邮箱比较使用规范化小写形式，并设置唯一约束。
- 老账号首次登录后提示绑定邮箱；新账号注册时同时填写找回邮箱。
- 邮箱验证完成前，账号可以登录和阅读，但不能投稿、评论、点赞、关注、收藏、修改资料或修改作品。
- 找回邮箱只用于验证身份、更换邮箱和重置密码。
- 普通成员、匿名用户和公开 API 均不能读取完整找回邮箱。

### 4.3 更换邮箱

更换找回邮箱需要：

1. 已登录会话。
2. 再次验证当前密码。
3. 旧邮箱验证码。
4. 新邮箱验证码。

旧邮箱不可用时只能进入管理员人工身份核验流程，不能只凭当前密码直接换绑。

### 4.4 密码找回

- 用户输入学号并完成 CAPTCHA。
- 无论账号是否存在、是否绑定邮箱，页面均返回相同的模糊提示。
- Edge Function 根据学号计算内部 Auth 邮箱并定位用户，但不向前端返回用户信息。
- 一次性重置令牌只保存摘要，具有过期时间、失败次数和使用时间。
- 重置成功后令牌失效，并注销其他会话。
- 请求按学号摘要、邮箱摘要和来源网络摘要限速；日志不得记录完整学号、邮箱、令牌或密码。

### 4.5 邮件发送与隐私

- 首次上线使用 Brevo 免费事务邮件服务，不购买自有域名。
- 普通公共邮箱作为已验证发件人时，Brevo 可以把实际事务邮件发件地址替换为平台提供的合规域名；页面和帮助文案必须提前说明该发件地址，避免成员误判为钓鱼邮件。
- 免费额度按每天 300 封设计。老用户邮箱绑定按每天最多 200 人分批开放，为验证码重发和密码找回预留容量。
- 同一账号或邮箱 60 秒内不能重发；单个账号每天最多请求三次同用途邮件，并同时执行来源网络限速。
- 邮件正文只包含用途、一次性验证码或安全链接、有效期和安全提示，不包含学号、笔名、作品、评论、关注、收藏或站内消息内容。
- 邮件服务商为完成投递必须处理收件邮箱，但应用不得向其发送不必要的社区资料。
- 后续取得自有域名后，可以只替换发件域名与 DNS 认证，不改变账号、邮箱绑定或密码找回数据。

## 5. 数据模型

### 5.1 `account_recovery_emails`

保存 `user_id`、规范化邮箱、验证时间、创建时间和更新时间。`user_id` 与邮箱均唯一。普通用户仅能通过受保护 RPC 获取脱敏邮箱状态，不能直接选择表数据。

### 5.2 `account_action_tokens`

保存邮箱验证、旧邮箱确认、新邮箱确认和密码重置令牌的摘要、用途、过期时间、失败次数、使用时间与关联用户。仅 Edge Functions 可访问。

### 5.3 `auth_rate_limits`

保存经过摘要处理的限速键、时间窗口和计数。仅 Edge Functions 可访问，定期清理过期窗口。

### 5.4 `work_versions`

保存：

- `work_id`
- 单调递增的 `version_number`
- 标题、摘要、分类和正文快照
- 修改说明
- `restored_from_version_id`
- 创建者和创建时间

`works` 保留作品身份、作者、状态、推荐状态和最新内容缓存，并增加当前版本指针。创建新版本与更新最新缓存必须在同一受保护 RPC 事务中完成。

### 5.5 `comment_quotes`

每条引用批注最多对应一个引用记录，保存评论 ID、作品版本 ID、引用原文、起止位置和创建时间。引用原文不可随作品后续版本变化。

### 5.6 `notifications`

保存接收者、触发者、事件类型、作品/版本/评论关联、精简载荷、创建时间和已读时间。RLS 只允许接收者读取和更新自己的通知。

### 5.7 `follows`

保存关注者和被关注作者的唯一关系。关注列表仅关注者本人可读。被关注作者只获得聚合关注者数量，不能读取关注者名单。

### 5.8 `bookmarks`

保存用户和作品的唯一收藏关系。收藏列表仅收藏者本人可读，收藏数量不公开，也不参与公开排行榜。

### 5.9 `comment_likes`

保存用户与评论的唯一“有启发”关系。公开查询只返回聚合数量，不返回点赞者名单。

### 5.10 `work_editorial_notes` 与 `comment_highlights`

只有管理员能创建或修改，保存推荐理由、编辑点评、管理员 UUID 和时间。普通用户只能读取针对公开作品和可见评论的公开编辑内容。

### 5.11 `reports` 与 `moderation_actions`

举报内容包含举报目标、类型、说明、举报者和状态。举报者身份仅管理员可见。管理员处置写入独立审计记录；前端无权删除审计记录。

## 6. RLS 与权限

- 新增 `is_recovery_email_verified()` 数据库函数，所有成员写策略和安全定义 RPC 均调用它。
- 未验证账号的数据库写请求必须失败，即使绕过前端直接调用 REST API。
- `notifications`、`follows`、`bookmarks` 只允许所有者读取自己的记录。
- `account_recovery_emails` 不授予匿名或普通 authenticated 角色直接表读取权限。
- `account_action_tokens` 与 `auth_rate_limits` 仅 Edge Functions 使用的后端身份可访问。
- 管理员编辑与处置能力通过 `profiles.role = 'admin'` 和受保护函数校验。
- `work_versions` 的已发布历史对所有读者公开；只有作品作者可以为自己的作品创建新版本，管理员不能冒充作者修改正文。
- 评论、批注和评论点赞只允许已验证账号创建。
- 举报者不能读取其他人的举报；被举报者不能读取举报者身份。

## 7. 查询、搜索与分页

### 7.1 作品分页 RPC

服务端接口接受搜索词、分类、排序、游标和页面大小。页面大小服务端硬限制为十篇。返回作品当前版本、作者公开资料、点赞数、评论数、当前用户点赞/收藏状态和下一页游标。

分页采用稳定游标而不是把全部作品下载到浏览器。相同排序值使用作品创建时间和作品 ID 作为确定性次级顺序，避免重复和遗漏。

### 7.2 正文搜索

搜索覆盖标题、摘要、当前版本正文和作者笔名。数据库为中文子串查询建立适用索引；搜索参数始终通过 RPC 参数传递，不拼接 SQL。

### 7.3 前端行为

- 输入停止约 300 毫秒后请求搜索。
- 新请求取消旧请求，旧响应不得覆盖新筛选状态。
- 搜索、分类或排序变化时重置为第一页。
- 桌面端点击“再读十篇”追加结果。
- 移动端在接近第八篇时预取下一批，但仍保持一次只重点展示一篇。
- 请求失败时保留已经加载的作品并显示重试入口，不把页面误显示成“0 篇”。
- 返回首页时恢复筛选、已加载批次和阅读位置。

## 8. 作品版本与引用批注

- 初次发布创建第 1 版。
- 修改作品时作者必须填写简短修改说明。
- 保存前携带当前版本号；版本号已变化时拒绝覆盖并提示重新载入。
- 最新阅读页只显示当前版本。
- 历史版本入口公开展示全部版本号、时间、修改说明和正文快照。
- 作者在历史版本页点击“恢复此版本”时，系统复制该内容生成新的最新版本，并记录来源版本。
- 普通读者只能查看历史，不能恢复版本。
- 读者可以选择当前可见版本中的连续文字并创建公开批注。
- 桌面端在正文旁显示批注入口；移动端在正文下方按引用顺序集中显示。
- 批注同时进入作品讨论和全站讨论页，并触发作者或被回复者的站内通知。

## 9. 私密社交与通知

- 收藏和关注列表仅本人可见。
- 取消收藏或关注不通知对方。
- 作者可以看到聚合关注者数量，但不能看到完整关注者名单。
- 关注作者发布新作时生成站内消息；短时间连续投稿合并提醒。
- 自己触发的动作不通知自己。
- 支持作品评论、评论回复、评论获赞、优质评论推荐和关注作者新作等消息类型。
- 消息页提供未读数量、单条已读和全部已读。
- 删除作品或评论后，历史通知保留事件说明，但不继续公开已经删除的正文。
- 找回邮箱永远不接收社区互动消息。

## 10. 管理员编辑与治理

- 不新增编辑角色；所有管理员同时拥有编辑能力。
- 作品推荐必须填写推荐理由，并记录管理员和时间。
- 优质评论推荐必须填写说明，并通知评论作者。
- 编辑点评独立于普通评论，清楚标注管理员身份和时间。
- 举报入口可用于作品、评论和账号公开资料。
- 举报处理结果必须选择明确状态并写入内部说明。
- 所有管理员处置通过受保护 RPC 完成并写入 `moderation_actions`。
- 投稿页显示原创、引用来源、排版检查和参与互评的提醒清单；清单只引导，不阻止发布。

## 11. 视觉与无障碍

采用已确认的“平衡阅读尺度”：

- 移动端正文默认 16px，行高约 1.9。
- 关键作者、日期、分类、版本和操作提示不低于 13px。
- 主要触控目标最小高度 44px。
- 弱化文字继续使用克制灰褐色，但保持可读对比度。
- 消息未读状态使用小型朱砂标记，不增加彩色图标或强动效。
- 关注、收藏、版本和批注入口位于正文之后或边栏，不长期占据阅读区域。
- 保留米白纸张、墨黑正文、暗红印章色、宋体标题、大量留白和细线。
- 不加入玻璃拟态、表情符号导航、普通商业卡片流或长期侧栏。

## 12. 错误处理

- 账号找回接口对存在和不存在的账号返回相同外部文案。
- 邮箱令牌过期、已使用或失败次数超限时提供明确但不泄露账号信息的提示。
- 数据查询失败时保留已呈现内容并允许重试。
- 创建版本、恢复版本、推荐和处置使用数据库事务，避免部分写入。
- 重复网络提交使用幂等标识或唯一约束消除重复通知、关注、收藏和点赞。
- 任何生产迁移失败都停止后续前端发布。
- 日志使用请求 ID 关联问题，不记录完整邮箱、学号、令牌、密码或作品正文。

## 13. 测试标准

### 13.1 单元与静态测试

- 分页游标稳定，无重复和遗漏。
- 正文搜索能够命中标题和摘要未出现的诗句。
- 搜索请求取消后不会覆盖最新结果。
- 通知路由不会通知触发者本人。
- 恢复旧版本生成新版本且不丢失历史。
- 引用批注保存正确版本、原文和位置。
- 关键样式满足 13px 元信息、16px 正文和 44px 触控目标。

### 13.2 数据库与 RLS 测试

- 匿名用户、未验证成员、已验证成员和管理员四类身份分别验证。
- 未验证成员的所有写请求被数据库拒绝。
- 通知、关注、收藏、找回邮箱和举报隐私不能越权读取。
- 普通成员不能设置推荐理由、推荐优质评论或写管理员审计。
- 作品版本和评论版本关联不可伪造。
- 迁移前后作品数量、作者 ID、正文快照和版本数量核对一致。

### 13.3 浏览器测试

- 老账号登录后完成一次邮箱验证并返回原目标。
- 新账号注册、验证、登录和找回密码流程通过。
- 首页首批仅十篇，桌面加载更多和移动预取通过。
- 正文搜索、筛选、排序和返回恢复通过。
- 评论、回复、批注、通知、关注、收藏和评论点赞通过。
- 修改作品、查看历史和恢复版本通过。
- 管理员推荐、点评、优质评论和举报处置通过。
- 桌面与移动端真实截图检查通过。

## 14. 环境与上线

- 现有 Supabase 项目继续作为生产环境。
- 新建空的 Supabase 测试项目，仅使用虚构账号和示例作品。
- 测试项目启用 Email Provider，关闭 Supabase 原生 Confirm email；找回邮箱由自定义流程验证。
- 测试项目 Site URL 使用本地测试地址，生产项目继续使用正式 GitHub Pages 地址。
- 测试项目的 Project URL 与 publishable key 只进入本地测试配置；生产发布配置继续指向现有生产项目。
- 每次运行数据库迁移或部署 Edge Function 前，必须显示并人工核对目标项目引用，测试与生产引用不相同才能继续。
- Publishable key 可以用于浏览器，但 Secret key、旧版 `service_role`、数据库密码和 Brevo SMTP/API 密钥只允许进入各自环境的受保护配置，禁止写入仓库、浏览器代码、日志或设计文档。
- Brevo 在邮箱功能进入集成测试前配置；正式环境不得依赖 Supabase 演示邮件服务。

上线顺序：

1. 备份生产数据库。
2. 在测试项目执行独立迁移和种子数据。
3. 部署 Edge Functions 并配置受保护密钥。
4. 完成 RLS 和浏览器自动化测试。
5. 经用户确认后按顺序执行生产迁移。
6. 发布 GitHub Pages 前端。
7. 使用专门测试账号完成线上邮箱、登录、投稿、搜索、分页、评论、通知、版本和举报冒烟测试。
8. 检查日志与数据库计数，不检查或输出真实用户私密数据。

## 15. 回退策略

- 前期迁移以新增表、索引、字段和函数为主，不立即删除旧字段。
- 新功能通过 `site_settings` 功能开关分阶段启用。
- 数据库迁移完成但前端尚未发布时，旧前端仍能运行。
- 功能异常时关闭对应开关并恢复上一版前端；已经产生的版本、通知和关系数据保留。
- 涉及数据转换的迁移在生产执行前必须完成备份、计数和内容抽样验证。

## 16. 交付拆分

本设计覆盖多个独立子系统，实施时分别编写计划并按顺序交付：

1. 账号验证、密码找回、限速与生产安全。
2. 聚合查询、正文搜索、十篇分页与视觉可读性。
3. 作品版本、恢复与引用批注。
4. 私密关注、收藏、评论点赞与站内消息。
5. 举报、管理员编辑能力和审计。

每个子系统完成测试和审查后再进入下一项，避免一次性高风险上线。
